## ARCHITECTURE SPIKE VERDICT

READY WITH CONDITIONS. Phase 1A can proceed to implementation review. Keep the interim restrictions until three properties are demonstrated independently:

1. Routine selection cannot reach real heavyweight work through pytest, including during collection or through a nested subprocess.
2. A second checkout cannot start heavyweight work while descendants of a crashed first run might still be alive.
3. The evidence reader rejects a PASS when the requested work, a required guard, cleanup, or authorization evidence is missing.

The smallest workable design keeps GateRun, the existing pytest and scenario judges, and the existing evidence store. Add one explicit selection contract, one admission layer shared by heavyweight entrypoints, and a run-wide deadline around the existing supervisors. A mutex plus a consumed authorization file is insufficient. The mutex owner, the process tree, and the evidence writer can die at different times.

## Recommended architecture and exact implementation specification

### 1. Resolve one explicit execution plan

Keep GateRun as coordinator. Have helpers/selection.py return an immutable ExecutionPlan containing mode, scope kind, normalized selectors, ordinary and guarded selections, named static checks, executable journeys or scenario, separate suggested obligations, required guards, effects, platform, mapping reasons and gaps. Reference the candidate and policy digest. All collections default to empty. Only the full-mode constructor can request the complete release partition. The executor validates the plan again before dispatch.

Use resolve(request, candidate, policy, inventory) → ExecutionPlan for preflight and execution. Use admit(plan, capabilities, authorization) → admitted scope or reason once at the execution boundary. Neither function imports test modules. Keep the existing coverage.json reader behind this interface. This removes the three overloaded None values without introducing a scheduler.

### 3. Changed selection and candidate identity

The current default is origin/master. _changed_selection diffs a merge base against working bytes with --no-renames, adds only four untracked subtrees, scans test source for module stems, and augments the result with coverage.json feature matches. Its always, prefix routes, full_on and no_selection rules can select guards on an empty diff, widen to the entire suite, or disregard tracked documentation. Diff contract

1. Without --base, anchor at the resolved HEAD. With --base REV, resolve exactly one commit, compute its unique merge base with HEAD, and include merge-base..HEAD. For an ancestor this is REV..HEAD; for divergent branches it is the candidate side since divergence. Resolve once and record the supplied ref, resolved SHA, merge base and HEAD. Invalid, ambiguous, unrelated or multiple-best-base histories require an explicit usable base. Never fetch automatically. A clean post-commit run needs --base HEAD^ or another intentional predecessor.
2. Union three distinct name-status streams: committed checkpoint changes, HEAD → index, and index → working tree, plus nonignored untracked paths across the repository. Use NUL-delimited Git output, --find-renames, byte-safe paths and explicit old/new names. Unioning streams preserves a staged change reversed in the working tree. Record that discrepancy and say which working bytes ran. Refuse unresolved index conflicts. Treat a rename Git cannot recognize as deletion plus addition.

Exclude outputs, scratch and owner-declared local-only paths according to Revision 4, including .ai/, scripts/project-status.py and files/run-temp/ while local-only. Apply privacy exclusions before reading content or writing path lists to exportable evidence. A newly tracked file at a private boundary is a policy error. Do not let a blanket README.md, md-instructions/, or string-prefix exclusion conceal tracked changes.

### 4. A5 machine-wide locking and abnormal recovery

Recommended invariant: before any heavyweight child can execute, the machine has both an exclusive live owner and a recoverable record that says earlier work may exist. The next owner must consult that record even if it opened a new mutex. A process-local finally, a dead launcher PID, and an absent scratch directory are individually insufficient.

| Platform | Recommendation, alternative and limitation |
|---|---|
| Windows | Use one stable machine name such as Global\ACT.Verification.Heavy. Do not include checkout, branch, user, session, mode or version in the name. Use non-inheritable CreateMutexExW, no initial-owner shortcut, then bounded WaitForSingleObject. Have one coordinator thread perform wait/release. Request SYNCHRONIZE, MUTEX_MODIFY_STATE and the rights needed to inspect security. Supply an explicit protected DACL granting those minimum rights to the approved participating principal(s), with owner/system administration. Validate the owner and effective descriptor of an existing object. Reject unknown creators, excessive write/control access, type collision, access denial, uninspectable state and unsupported sandbox/nested-job conditions. Never fall back to Local\. Default to same owner across logon sessions; an unapproved different account receives BLOCKED. Do not relax the integrity label for a low-integrity worker. | macOS | Prefer nonblocking exclusive flock on one pre-provisioned stable inode on a local filesystem, shared by every participating checkout and session. Recovery state and process ownership

- Use one machine-agreed control location. For this Windows development machine, the proposed home is a protected, ignored control area of the permanent development checkout. Independent candidate checkouts must address that same control area. On Mac, the stable flock file can also hold the recovery state. Validate the authority location and identity; a caller cannot substitute its current checkout or specify a private authority on the CLI. Provision it once with the machine quiescent. A missing initialized store, bad checksum, partial write, replaced inode or unavailable authority blocks admission. Exclude it from disposable-output cleanup and evidence-directory discovery. The current %TEMP%\act-gate exception covers scratch children only.
- Under the lock, durably record active with run ID, candidate, boot identity, coordinator PID and start identity, ownership method and the intended child domain, before launch. Flush the state. Write clean only after the last spawn is disabled, all owned work is proved gone and required cleanup is accounted for. A torn update has the conservative meaning recovery-required. On macOS, keep the flock inode stable when updating the record; atomic replacement of the locked file would create a second lock domain.
- Put all Windows heavy workers under one outer kill-on-close job without breakaway. Keep existing per-stage and low-integrity jobs where nesting succeeds. Prefer assigning the first worker at creation using PROC_THREAD_ATTRIBUTE_JOB_LIST; the current suspended-then-assign sequence has a coordinator-crash window leaving an unowned suspended process. Descendants inherit the outer job. Refuse launch routes that delegate work outside it, including shell/OS service handoffs, unless their independent ownership is proved. Use kernel job membership/accounting for drain. WAIT_ABANDONED transfers mutex ownership for recovery only. A newly created mutex after every old handle closed must perform the same recovery check. - On Mac, retain process groups for ordinary termination. For a real app, nested group, or session leader, reuse the existing guardian/lifeline and kernel start-time checks where they cover the launch. Register the intended spawn before permitting it to proceed. On parent loss, close the launch channel, stop new work and drain every registered group/worker. ### 5. A6 owner-issued scoped authorization

Use a separate verify.py authorize command, run by the owner at an interactive terminal. Show the physical checkout, candidate, dirty state, native platform, exact scope, side effects, network policy, budget, expiry and number of attempts. Minimum fields: schema version, random grant ID, issuer workflow and issuance time, canonical repository and checkout identity, HEAD/index/working-tree/policy digests, native OS and architecture, mode, normalized scope digest and exact scenario/journey/effect set, permitted network policy, expiry UTC, wall/idle limits, attempts allowed, cumulative budget, state, and immutable claim records with run ID and timestamps. A grant defaults to one attempt. Bounded remediation lists the permitted subscopes, maximum attempts and aggregate budget in advance. A modified candidate needs fresh authorization. No wildcard “continue until green.”

Order of operations

1. Parse and perform non-invasive checks. Resolve scope, candidate, capabilities, disk and estimated cost. A diagnostic exits here.
2. Read and provisionally validate the grant. Reject missing, revoked, expired, malformed, wrong-platform, wrong-checkout, mismatched candidate, effect, scope or budget. Produce no heavyweight side effect.
3. Acquire A5 and reconcile the prior recovery state. Lock denial consumes nothing: no execution opportunity was obtained.
4. Under A5, resolve/recheck candidate, exact scope, current time, prerequisites and budget. Atomically claim one attempt with a conditional transaction, unique run ID and sufficient remaining budget. Serialize revoke/claim in the same store. A concurrent loser gets no claim. Reserve the attempt’s budget conservatively so a crash cannot create unmetered remediation.
5. Durably mark the machine active, establish the owned child domain and validate the live delegation before permitting real work. A crash between claim and launch spends that attempt. A crash between machine marking and launch may require recovery even if no child started. This asymmetry prevents double spending.
6. Revalidate at each heavyweight stage and immediately before a new heavy child/effect. Treat expiry as a limit on new work and cap the active execution deadline at the grant’s validity. Stop on candidate/policy change, revocation or deadline. Hash again at completion. For data that can change between validation and consumption, pass the already-read validated bytes/handle or use a validated immutable stage input. An independently editable checkout cannot be frozen by a pre-launch hash. Where a stage reopens mutable executable inputs and cannot establish a stable candidate, require an exclusive candidate workspace or block that stage.
7. Stop launches, drain and verify descendants, finish evidence, record actual spend/outcome, then clear the machine recovery state and release the lock. Cancellation, failed cleanup and a lost wrapper never refund an attempt. A new attempt is possible only within an explicitly bounded surviving grant or after fresh issuance. Revocation prevents future claims and future stages; it triggers controlled cancellation of active work.

A result records the grant ID/digest, claim and run IDs, approved versus used scope, budget and terminal disposition. It must not contain a reusable launch credential. Bind a child’s authority to the running parent so a sealed historical result cannot be replayed as permission. No cloud service, administrator account, credential or signing infrastructure is required.
