## 1. Purpose

Redesign the MP3 Tool as a **multi-book MP3 metadata editor and processor** built on the shared Plan-3 and Plan-6 foundations.

The finished tool has two primary processing actions:

1. **Write ID3 Tags**
2. **Combine MP3s → One MP3**

Each action processes **all eligible Books sequentially in Book order**.

The redesign covers the complete MP3-specific workflow:

- dynamic multi-book importing and navigation;
- ordered MP3 lists per Book;
- Shared versus Book metadata;
- source-metadata prepopulation;
- chapter/track title editing;
- deterministic filenames and track numbers;
- signed end-time adjustment;
- artwork selection and embedding;
- intentionally clean ID3 output;
- one MP3 Tool run containing one subfolder per Book;
- continue-on-book-failure;
- progress, Pause/Resume/Cancel and Retry Failed;
- and the first production adoption of a reusable **single Summary/Detailed log region**.

This is a substantial tool-specific redesign. It is not a cosmetic patch to the existing single-book panel.

## 4. Explicit MP3-specific supersessions

The requirements in this section are binding for this focused work. They supersede the listed older MP3-specific assumptions without editing the permanent historical documents now.

| Older assumption | Current binding requirement |
|---|---|
| Bulk ID3 preserves existing tags by default, optionally clearing all first. | Every generated MP3 uses an intentional clean metadata whitelist. Old unwanted user-facing ID3 metadata is removed. |
| Combine has Preserve-majority and Remove-all metadata modes. | There are no such runtime modes. Artist / Album Artist / Album resolve `Shared -> Book -> blank`. Source majority is only initial editable UI data. |
| Combine always removes artwork. | Old source artwork is removed, but explicitly selected effective Shared/Book artwork is embedded in the newly generated combined MP3. |
| MP3 work waits for the old later Plan-8 sequence. | The maintainer explicitly directs focused MP3 implementation now on the current Plan-6 feature branch. |
| Original Plan 6 closes with `mp3_tool.py` byte-identical and no production adopter. | That protection is superseded **for `mp3_tool.py` only** by this focused continuation. M4B Maker and M4B Metadata remain protected. |
| The generic uncommitted Phase-8 workspace prototype is the final UI destination. | The prototype is salvage material only. The MP3-specific workflow determines the final layout and component boundaries. |
| Separate standalone Time Edit operation. | Remove it from the primary workflow. Signed end-time adjustment is part of both main process modes. |
| Separate `Silence between tracks` control. | Remove it. There is exactly one signed `Add/Remove Time at End of Each Track (seconds)` value. |
| User chooses a FAST-mode checkbox. | Remove the checkbox. Combine automatically tries FAST when valid and automatically falls back to Safe. |
| Combine asks for an output filename popup on every run. | Remove the popup. The Book's deterministic Album/source-folder/Book-N fallback determines its combined filename. |

These supersessions are scoped to this MP3 redesign. Do not use them as permission to change unrelated tools.

## 9. Architecture

### 9.1 Separation of responsibilities

Keep four distinct concerns:

**Shared Plan-6 model**

Owns Book identity, workspace mutation, Shared precedence, frozen Book snapshots, dispositions and retry contracts.

**MP3 workflow/domain layer**

Owns MP3-specific semantics such as:

- metadata observation;
- majority calculation;
- default track titles;
- title-line application;
- naming;
- signed-time parsing;
- MP3 output metadata;
- Book output planning data.

**MP3 media-processing layer**

Owns:

- FFmpeg invocations;
- MP3 copy/time adjustment;
- FAST/Safe Combine;
- timestamp generation;
- final ID3/APIC writes;
- temporary staging and publication.

**MP3 Tk consumer**

Owns widgets and callback routing only:

- reads widgets on the main thread;
- writes changes into immutable workspace values;
- captures a frozen run;
- starts one worker;
- renders typed events;
- never lets the worker read Tk.

### 9.2 Keep `mp3_tool.py` manageable

The current file is already large. The redesign must not turn it into a monolith containing:

- UI;
- import orchestration;
- metadata probing;
- naming;
- FFmpeg processing;
- artwork conversion;
- retry merging;
- output publication;
- logging projection.

Prefer extracting MP3-specific pure/processing helpers into one or two focused modules, for example:

- `mp3_tools/mp3_workflow.py`
- `mp3_tools/mp3_processing.py`

Exact names may be adjusted after Phase-1 source audit, but do not create a directory full of micro-modules.

`mp3_tool.py` should remain the production panel/orchestration entry point and keep its stable `build_ui(parent)` boundary.

## 11. Source metadata observation and initial UI prepopulation

Source metadata is an **editing aid**, not output fallback.

### 11.1 Observation

When compatible MP3s first populate a Book, inspect their ID3 tags read-only.

Observe, at minimum:

- Title;
- Artist;
- Album Artist;
- Album.

Do not import source:

- Year;
- Genre;
- Composer;
- Comment;
- embedded artwork;
- arbitrary freeform frames

into the final output contract.

### 11.2 Majority values

For:

- Artist;
- Album Artist;
- Album

compute one deterministic agreed/majority initial value.

Comparison should normalize enough to avoid cosmetic disagreements being treated as separate values, including:

- Unicode normalization;
- surrounding whitespace;
- repeated whitespace;
- case-insensitive comparison.

Preserve a natural source spelling for the chosen displayed value.

If multiple normalized source values exist, visibly mark the corresponding Book field as:

**Mixed source metadata**

Tie behavior must be deterministic. Prefer the first value encountered in the Book's current natural source ordering among equally common candidates.

A missing/blank source value participates honestly in disagreement detection; do not fabricate metadata where the files predominantly provide none.

### 11.3 Do not overwrite later user edits

Initial automatic prepopulation occurs when:

- a folder import creates a Book; or
- an empty Book receives its first manually added files.

When more files are later added to a Book that already contains inputs:

- retain the user's existing scalar Book field values;
- observe the newly added source metadata;
- update source-mixed diagnostic state as appropriate;
- do not silently replace a value the user has typed or intentionally cleared.

This is important because clearing a pre-populated field must mean “write blank,” not “please restore the source value.”

### 11.4 Track-title seed data

For each imported MP3 occurrence capture an immutable initial/default title:

1. nonblank useful source ID3 Title, if available;
2. otherwise a cleaned title derived from the source filename.

The default-title observation should be associated with the imported occurrence identity, not with a bare path or row index.

This source-title seed is allowed as the fallback for that track's **Title only**, because that is the explicitly required track-title behavior.

It must **not** become a hidden fallback for Artist, Album Artist, or Album.

### 11.5 Adding/removing/reordering files

Occurrence identity must keep title seeds aligned when tracks are:

- reordered;
- removed;
- added.

Do not maintain a fragile second parallel Python list indexed only by row number.

## 12. Import model

### 12.1 Startup

The MP3 Tool begins with:

- one empty Book;
- Shared area visible;
- current Book = Book 1 of 1;
- Auto-number enabled;
- blank Start #, interpreted as 1;
- no artwork selected.

### 12.2 `Import Folder`

`Import Folder` is workspace-level and appears once near the top.

It uses the existing shared Plan-3 importing machinery.

The user selects one parent directory.

Recursively discover compatible MP3s.

Each directory that **directly contains** one or more compatible MP3s becomes exactly one Book.

Examples:

```text
Parent/
  Book A/
    01.mp3
    02.mp3
  Book B/
    Part 1/
      01.mp3
      02.mp3
    Part 2/
      03.mp3
```

produces:

```text
Book A
Book B/Part 1
Book B/Part 2
```

Distinct containing directories must never merge.

Files in a containing directory are naturally/deterministically ordered.

### 12.3 Folder-import transaction

Retain the established Plan-6 replacement semantics unless a later maintainer instruction changes them:

- scan first;
- commit atomically only after successful scan/confirmation;
- project the committed snapshot into Books;
- replace the current workspace as one operation;
- cancellation/failure before commit leaves the existing workspace unchanged.

If the current workspace contains meaningful work, use the existing meaningful-work contract to protect against accidental loss before replacing it.

Do not invent append-vs-replace heuristics.

### 12.4 Unsupported/skipped entries

Unsupported files are:

- not imported;
- not treated as fatal simply because they coexist with MP3s;
- reported through the existing import problem/reporting architecture.

Preserve current safety rules for:

- links/junctions;
- hidden entries;
- unreadable entries;
- vanished entries;
- cancellation;
- broad roots;
- large results.

### 12.5 `Add Files`

`Add Files` belongs to the current Book.

Every selected compatible MP3 goes into that current Book regardless of source parent directory.

Do not regroup manually selected files by parent folder.

Use the shared direct-file validation/transaction contract.

### 12.6 Track-list operations

For the current Book support:

- Add Files;
- Move Up;
- Move Down;
- Remove Selected.

A Clear-all shortcut may exist only if it adds real value and follows meaningful-work confirmation. It is not required.

The list is a view of the Book's immutable imported-file snapshot, not a second source of truth.

## 16. Title, filename and Track Number are independent

These are three different values.

Example:

Source/output filename:

```text
02 Chapter 741_ Home Again.mp3
```

Embedded Title:

```text
Chapter 741: Home Again
```

Embedded Track Number:

```text
2
```

Never place the filename prefix inside the embedded Title.

### 16.1 Source-derived title cleaning

When deriving a Title from a filename:

- remove a leading track-number prefix;
- remove associated separator punctuation/spacing;
- convert the filename's title separator `_` into user-facing `: ` where appropriate;
- collapse accidental repeated whitespace;
- preserve the actual chapter number inside text such as `Chapter 741`.

Do not strip numbers that are part of the real title after ordinary words.

### 16.2 Output filename normalization

When Auto-number is enabled:

1. take the source-derived basename;
2. remove an existing leading track number;
3. sanitize the remaining name for cross-platform output;
4. add the newly calculated track number exactly once.

Never produce:

```text
02 17 Chapter...
```

from an already numbered source.

### 16.3 Number width

Filename numbering uses one consistent width for the Book:

- minimum width = 2;
- widen automatically when the highest calculated number requires more digits.

Examples:

```text
01
02
...
99
100
```

For a range whose final number is 101, use a width capable of representing 101 consistently.

### 16.4 Start #

Start # is Book-only.

Blank means:

```text
1
```

A nonblank invalid value must produce a clear validation error; do not silently reinterpret arbitrary invalid text as 1.

Start # should be a positive integer.

### 16.5 ID3 Track Number

When Auto-number is enabled:

```text
1
2
3
...
```

Write ordinary numeric text to ID3 `TRCK`; zero-padding is a filename presentation concern.

When Auto-number is disabled:

- omit Track Number from the clean output metadata;
- do not add output filename numbering;
- retain the sanitized source basename subject to collision safety.

### 16.6 Relationship to Plan-6 success-only numbering

Do not force `SuccessNumbers` into a problem it does not represent.

Per-track MP3 numbering is a **frozen positional property of tracks inside a Book**, not a cross-Book success-consumed sequence.

Because a failed Book publishes no partial final result, failed intermediate tracks do not expose numbering gaps in a published Book.

`shared.numbering.py` remains the sole success-only allocator for workflows that genuinely consume sequence numbers on success. Do not create another allocator inside MP3 code.

## 17. Signed Time contract

There is exactly one field:

**Add/Remove Time at End of Each Track (seconds)**

It exists:

- Shared; and
- per Book.

Normal Shared precedence applies.

Accepted semantics:

```text
positive -> append that duration to the end
negative -> remove that duration from the end
zero     -> no duration adjustment
```

The value should be a finite numeric number.

Reject:

- NaN;
- infinity;
- malformed nonblank text.

For trimming, never request an invalid negative/zero finished duration. If the requested trim is too large for a source track, fail that track/Book with a useful error rather than manufacturing corrupt output.

Zero means **no duration change**, not “skip processing.”

## 18. Output metadata whitelist

Every generated individual MP3 intentionally retains/writes only:

- Title;
- Artist;
- Album Artist;
- Album;
- Track Number, when Auto-number is enabled;
- effective selected Book Artwork, when present.

Remove user-facing source metadata not intentionally allowed, including:

- Year;
- Genre;
- Composer;
- Comment;
- old embedded artwork;
- arbitrary TXXX/freeform source tags;
- ReplayGain/source identifiers unless technically required for valid audio playback;
- stale Track Number when Auto-number is off.

Do not damage the MP3 audio bitstream/container data required for playback.

Prefer writing the final whitelist from a clean ID3 tag state rather than attempting to enumerate every unwanted old frame one by one.

Automated tests should inspect the actual resulting ID3 frame IDs rather than assuming an EasyID3 key deletion removed all possible source frames.

## 19. Artwork architecture

### 19.1 Selection

Artwork is explicitly selectable:

- once in Shared;
- separately in every Book.

Provide:

- Choose;
- Clear;
- visible preview.

The preview behavior should be similar to the existing M4B Maker, but capability detection must come from the shared image infrastructure.

### 19.2 Accepted source formats

Build the artwork chooser's file filter from:

`shared.image_capabilities.decodable_suffixes()`

not from a hard-coded JPG/PNG list.

Therefore:

- JPG/JPEG and PNG are always offered;
- HEIC/HEIF are offered when the shared capability probe says the machine can decode them.

Do not build another HEIC probe.

### 19.3 Source safety

Selected artwork is read-only.

Never:

- resize the source;
- crop the source;
- overwrite the source;
- write a converted file beside it;
- mutate EXIF/source data.

The existing Cover Image tool remains the workflow for resizing/cropping.

### 19.4 Preview

Preview decoding may scale a temporary in-memory UI representation for display.

That preview resize has no effect on the embedded output image.

The selected file's path/value remains the source of truth.

### 19.5 APIC output

Use Mutagen's normal ID3 APIC representation with a front-cover picture type.

For JPG/JPEG or PNG input:

- embed the source image bytes directly when they are valid and decodable;
- use the correct MIME type;
- do not re-encode or resize merely for embedding.

For HEIC/HEIF input:

- use the existing shared decode capability;
- decode the selected image;
- create an **output-embed-only PNG representation in memory**;
- preserve pixel dimensions;
- do not resize/crop;
- do not modify the selected image;
- embed those PNG bytes as the APIC front cover.

Do not create a persistent PNG sidecar merely to tag the MP3.

This is the narrow interoperability conversion for ID3 embedding, not a new image-conversion subsystem.

### 19.6 No artwork selected

If neither Shared nor Book artwork is populated:

- old embedded source artwork is removed;
- output contains no APIC artwork.

### 19.7 Shared override

When Shared artwork is selected:

- it wins for every Book;
- each Book's artwork chooser becomes disabled;
- the Book's stored artwork path remains intact.

Clearing Shared artwork restores the Book artwork selection and preview.

## 21. Atomic Book publication

A Book is the publication boundary.

A failed Book must not leave what appears to be a successful partial Book result.

### 21.1 Staging

- time-adjusted MP3s;
- normalized WAVs;
- concat lists;
- temporary combined MP3;
- timestamp data;
- temporary tag-write artifacts.

Prefer a clearly internal directory such as a dot-prefixed or otherwise reserved `.work` area under the one run.

### 21.2 Publish boundary

For Write ID3:

- all intended Book tracks must finish successfully;
- all metadata/artwork writes must finish;
- all outputs must pass bounded validation;

For Combine:

- all required per-track processing must finish;
- FAST or Safe combine must finish;
- final metadata/artwork must finish;
- timestamp file must finish;
- bounded validation must pass;
- only then publish the Book result.

### 21.3 Failure

On Book failure:

- no partial final Book folder is presented as successful;
- private staging may remain when required for retry;
- mark the Book failed;
- continue to later Books where safe.

On final abandonment/cleanup, delete only this run's own private staging.

Never delete source media.

## 22. Frozen run capture and retry reconciliation

### 22.1 Capture everything the worker needs

Before a worker starts, freeze each eligible Book's complete effective processing state, including:

- operation mode;
- ordered occurrence IDs/files;
- effective Artist;
- effective Album Artist;
- effective Album;
- effective signed Time;
- effective artwork source;
- Auto-number state;
- normalized Start #;
- complete resolved track-title tuple;
- final planned Book folder;
- final planned filenames;
- combined output filename where applicable;
- any required source-title seed data;
- relevant output/run planning state.

The worker must not read live widgets or reconstruct configuration from the current workspace later.

### 22.2 Existing Retry Failed contract stays authoritative

Use:

- `WorkspaceRunResult`;
- `retry_failed_books(...)`;
- each Book's existing Plan-3 `RetryRequest`.

Do not create:

- `MP3RetryRequest`;
- a new retry enum;
- a new retry controller;
- a retry-specific rebuilt workspace.

### 22.3 Important retry/publication reconciliation

Plan-6 Retry Failed deliberately retries the failed **item subset** from the exact original Book snapshot.

This focused redesign also requires Book-atomic publication.

Therefore:

- successful track/stage results from a failed Book may remain in **private unpublished staging**;
- the retry processes the exact failed items requested by the frozen `RetryRequest`;
- already successful staged pieces are reused rather than regenerated from today's GUI;
- after the failed items succeed, the Book can finish/finalize and publish atomically.

Do not solve this by widening a RetryRequest to “all tracks in the Book.”

### 22.4 Fatal/unretryable Book failures

Retain Plan-3 semantics:

- an item-scoped retryable failure may produce Retry Failed;
- a genuine fatal job/book-level failure represented by an item-less fatal record remains unretryable.

Do not falsify an item identity merely to make a Retry button appear.

The UI may still show the Book as Failed; Retry Failed is offered only where the existing foundation says it is valid.

### 22.5 Retry merge

If a reusable pure helper is missing for replacing failed per-Book `RunResult`s after a retry, add the smallest generic composition helper to the Plan-6 layer.

It must:

- retain the original `BookRunSnapshot` object;
- accept results only for Books actually retried;
- require the original Book `RunSnapshot` object identity;
- replace only the prior failed Book result;
- preserve untouched Book results;
- derive the new batch state honestly.

This is an evolution of the existing result composition, not a new retry framework.

## 23. Write ID3 Tags — execution contract

Button label:

**Write ID3 Tags**

It processes all eligible Books sequentially in Book order.

Within one Book, process tracks in frozen track order.

For every track:

1. source remains read-only;
2. create a clean staged output;
3. apply positive/negative signed Time when nonzero;
4. when Time is zero, still create a new clean output;
5. remove old unwanted metadata/artwork;
6. write final Title;
7. write effective Artist when populated;
8. write effective Album Artist when populated;
9. write effective Album when populated;
10. write Track Number when Auto-number is enabled;
11. embed effective artwork when provided;
12. use the planned final filename;
13. validate the staged result sufficiently to detect obvious failed/corrupt output.

If one track fails:

- record a real item-scoped failure against that occurrence where applicable;
- keep prior successful output private;
- stop processing that Book when continuing cannot contribute safely;
- mark that Book Failed;
- continue to the next Book.

Do not publish the partial Book.

### 23.1 Zero-Time copy

Zero Time must still strip/rewrite metadata.

A stream-copy approach such as FFmpeg `-map_metadata -1 -c copy` may be retained when valid, followed by the intentional Mutagen whitelist write.

Zero Time is not a no-op.

### 23.2 Positive Time

Append the requested duration at the **end of every track**.

### 23.3 Negative Time

Trim the requested amount from the end of every track.

Fail safely if the requested trim would make the output invalid.

## 24. Combine MP3s → One MP3 — execution contract

Button label:

**Combine MP3s → One MP3**

It processes all eligible Books sequentially.

Each Book produces exactly **one** combined MP3.

Different Books are never combined.

### 24.1 Signed Time before combine

Apply the effective signed Time to **every constituent track before combination**.

Positive:

- append time to each track;
- including the final track.

Negative:

- trim every track.

Zero:

- no duration adjustment.

There is no separate inter-track gap concept.

### 24.2 FAST first

When the frozen inputs/options allow a valid FAST path:

1. automatically try FAST;
2. if FAST fails in a way where Safe processing remains valid, record the reason;
3. automatically switch to Safe;
4. continue without user intervention.

There is no FAST checkbox.

A FAST path must never be used merely because it is quicker when its assumptions are invalid after signed-time preprocessing or other required transformations.

### 24.3 Safe path

Reuse the proven WAV-normalization/concat concepts from the current source.

Do not redesign the audio encoder without need.

### 24.4 Combined metadata

Final combined MP3:

```text
Title        = effective Album
Artist       = effective Artist / Author
Album Artist = effective Album Artist / Author
Album        = effective Album
Track Number = none
Artwork      = effective Book Artwork
```

If effective Album is blank, the combined embedded Title is blank/absent according to the clean whitelist contract. Do not secretly substitute the source folder name into embedded Title merely because the filename uses it.

### 24.5 Combined timestamps

Retain `combined_time-stamps.txt`.

Its chapter/track labels use the same final effective resolved track Titles used by the run.

Timestamp offsets must reflect the **post signed-time-adjustment** durations actually combined.

Do not implement embedded MP3 chapters.

## 25. Job control and batch orchestration

### 25.1 One controller per operation attempt

Preserve the Plan-6 rule:

**one `JobController` per batch run/attempt, not one per Book.**

Pause, Resume and Cancel apply to the overall operation.

Do not create ten controllers for ten Books.

### 25.2 Sequential Book loop

Pseudo-contract:

```text
capture frozen workspace run
start one batch controller

for Book in frozen Book order:
    checkpoint
    if Book skipped:
        record skipped
        continue

    mark Book Processing
    run that Book against its frozen snapshot

    if Book succeeds:
        publish atomically
        mark Completed
    else:

        retain only safe retry staging
```

- before a Book;
- between tracks;
- between major FFmpeg stages;

On acknowledgement:

- do not start later Books;
- clean unpublished partial work that is not intentionally retained;
- preserve already completed/published Books;
- settle later Books according to existing `NOT_ATTEMPTED` semantics;
- do not invent a sixth `BookDisposition.CANCELLED`.

### 25.5 Input locking

Lock:

- Shared fields;
- Book fields;
- artwork selection;
- import;
- Add Files;
- reorder/remove files;
- Add/Duplicate/Remove Book;
- processing buttons.

Leave appropriate job controls/log interaction available through the existing availability matrix.

Do not let a changing GUI alter a frozen operation.
