### Preferred order of investigation

When a quality defect is observed, investigate in this order unless evidence clearly points elsewhere:

1. source text / segmentation correctness;
2. where and why audio units are split;
3. assembly/rejoining and inserted silence;
4. avoidable lossy re-encoding / bitrate / container or duration metadata;
5. only then backend generation parameters or engine-specific tuning.

This order reflects the maintainer's current experience: most timing problems appear more likely to come from piecing generated audio back together than from the underlying voices themselves.

### Historical behavior that must be treated as evidence

The maintainer reports that the v0.5.0-era **Edge folder-batch mode sounded very good**, had near-ideal synthesis speed, and did **not** have a meaningful between-track timing problem. Known concerns were principally:

- incorrect player-reported/file-duration timing metadata in some outputs; and
- some perceived fuzziness / quality loss.

Therefore:

- do not assume the historical batch pacing needs to be redesigned;
- separate duration/container-metadata defects from audible timing defects;
- investigate whether fuzziness comes from the Edge service itself, final encoding settings, or avoidable additional lossy generations;
- use the historical batch behavior as an auditory/performance reference, not as code that must be blindly restored byte-for-byte;
- retain later correctness/security/job-control fixes even if the selected audio behavior resembles the older batch path.

Kokoro has generally sounded good and should receive only small evidence-backed changes. Chatterbox work should concentrate on demonstrated long-silence and pronunciation-stability defects, not broad retuning.

### Explicitly out of scope

Do not:

- reintroduce EPUB;
- redesign unrelated tools;
- alter M4B Maker / Metadata Editor behavior;
- replace tkinter/ttk;
- add another TTS model;
- replace Chatterbox Turbo;
- perform a wholesale rewrite of Edge, Kokoro or Chatterbox merely for symmetry;
- add user-facing Chatterbox tuning controls;
- add Whisper/faster-whisper or another large speech-to-text runtime dependency for v0.6.5;
- normalize every chunk independently;
- add a pronunciation dictionary or hard-code one-off replacements such as `Ascended` / `Tamar`;

## 6. Core Quality Principle and Research Contract

There is no universal TTS post-processing recipe assumed correct before listening.

The governing rule is:

> **Preserve what already sounds natural. Change the smallest seam that explains a demonstrated defect.**

A measurable timing improvement that sounds worse is a regression. A cleaner abstraction that changes a voice for the worse is also a regression.

### Assembly-first hypothesis

The working hypothesis for v0.6.5 is that many audible defects are more likely to arise at boundaries created by chunking, joining, inserted silence, or repeated encoding than from the underlying TTS voices themselves.

This is a hypothesis to test, not a predetermined conclusion. The quality work should therefore isolate:

```text
raw/backend-generated audio
text segmentation
chunk boundaries
trim decisions
inserted pauses
assembly/rejoining
final lossy encoding
container/duration metadata
```

before changing engine generation settings.

### No preselected universal recipe

Do not begin by assuming all engines require values such as:

```text
-50 dBFS trim
35 ms crossfade
350 ms sentence pause
700 ms paragraph pause
24 kHz forced resampling
programme loudness normalization
```

Any of these may be evaluated as candidates when a specific defect justifies the experiment. None is a release requirement.

### External Reference Research Contract

External repositories are design references only. They are not dependencies, submodules, vendored code, or authorities over this project's measured behavior.

Before adopting a technique inspired by another repository, the implementing agent should:

1. inspect the actual relevant source, not rely on README/LLM/search summaries;
2. identify the smallest useful mechanism;
3. implement it within this project's existing architecture;
4. preserve FFmpeg trust/provisioning, source immutability, output planning and shared job controls;
5. avoid a new dependency unless the current experiment proves a meaningful benefit and the maintainer approves it;
6. test it first as a bounded candidate/QA seam where practical;
7. compare against the established baseline using identical text and, where practical, identical raw generated audio;
8. reject it if it sounds worse even when a metric improves.

Do not copy substantial external implementation code without first checking license compatibility and preserving required attribution. Prefer a narrow reimplementation of the studied technique.

#### Reference A — `loserbcc/open-unified-tts`

This repository is archived/static reference material, not an active upstream dependency.

Useful ideas:

- natural-boundary chunk sizing;
- PCM/WAV-domain stitching;
- a very short crossfade as a **candidate** for a technical continuation seam.

Do not inherit its per-chunk peak normalization, generic resampling, forced mono behavior, bare `ffmpeg` invocation, or universal crossfade policy.

#### Reference B — `zeropointnine/tts-audiobook-tool`

Primary external design reference for:

- mature sentence/phrase segmentation (`pysbd` as one candidate);
- explicit semantic boundary reasons;
- relative-RMS edge-silence analysis;
- excessive-silence QA;
- true two-pass FFmpeg `loudnorm` if final programme normalization is ever justified;
- optional STT verification as future research.

Do not import its whole architecture or dependency set.

#### Reference C — `nikkoxgonzales/streaming-tts`

Useful mainly for target-size vs absolute-maximum chunking and separation of text normalization from synthesis. It is not the authority for abbreviation-safe sentence splitting.

#### Reference D — `psdwizzard/chatterbox-Audiobook`

Secondary QA/UX reference for audio measurements and structural handling. Do not treat its peak normalization as an EBU-R128 implementation.

### Primary engine authorities

Engine-specific evidence from the exact versions this project uses takes priority over generic audiobook projects:

- Microsoft Edge / `edge-tts` behavior for Edge;
- Kokoro upstream/current repository evidence for Kokoro;
- the exact pinned `chatterbox-tts` version plus this repository's Chatterbox tests and listening decisions.

### 8.1 Chatterbox — preserve proven tuning; investigate pronunciation and long silence

Preserve by default:

```text

GENERATION_TEMPERATURE = 0.72
GENERATION_TOP_P = 0.95
GENERATION_TOP_K = 1000
GENERATION_REPETITION_PENALTY = 1.2

```

Also preserve the proven reference-conditioning contract, model-native/PCM assembly path, one final lossy MP3 encode, safe cancellation boundaries, and current single-file-worker limitation where shared model state requires it.

Do not route Chatterbox back through Kokoro's 3,000-character splitter and do not pre-normalize reference recordings.

#### Pronunciation investigation

Pronunciation is a genuine v0.6.5 Chatterbox quality concern, but a word-specific pronunciation dictionary remains out of scope.

Existing repository evidence is important:

- `Ascended` had previously been pronounced incorrectly under less-stable sampling and was explicitly reported correct at the selected `0.72` temperature;
- `Tamar` was documented as varying between pronunciations within one chapter;
- existing regression tests deliberately prohibit hard-coded word replacements / pronunciation maps for those examples.

Treat these as evidence about **sampling stability, text context, segmentation and engine behavior**, not permission to replace specific words.

When a current pronunciation defect is reproducible:

1. capture the exact text/context and voice;
2. determine whether the problem changes with segmentation/context or repeated generation under the existing settings;
3. inspect the exact pinned Chatterbox engine for any legitimate supported pronunciation/phoneme mechanism before inventing one;
4. prefer the smallest general fix that improves the demonstrated class of problem;
5. preserve `0.72` unless a bounded A/B test proves a better setting without degrading the rest of the voice;
6. if the problem cannot be fixed cleanly without a broad pronunciation subsystem or one-off word hack, document/defer it and return to the maintainer rather than expanding scope silently.

Long unexplained silence should likewise be traced to model output vs segmentation/assembly before altering generation parameters.

### 8.2 Kokoro — minimal changes only

Preserve:

- model-native PCM output;
- native 24 kHz behavior;
- no needless intermediate MP3 generation;
- one final MP3 encode;
- current language mapping and voice set;
- current 3,000-character limit unless evidence clearly supports another value.

Kokoro has generally sounded good. Do not retune or restructure it merely because Edge requires work. Investigate only demonstrated join, silence, segmentation or pronunciation defects.

### 8.3 Edge — preserve the good batch character and isolate fuzziness/metadata defects

Edge needs the largest **assembly/path audit**, not necessarily the largest engine rewrite.

The maintainer's v0.5.0-era folder-batch experience is an explicit reference point:

- speech pacing sounded very good;
- between-track timing was not considered a problem;
- synthesis throughput was close to ideal;
- the notable correctness issue was inaccurate reported/file duration timing metadata;
- some output sounded slightly fuzzy.

Phase 1/3 should locate the historical implementation/evidence in Git history and compare it with the merged v0.6.4-era path without blindly reverting later fixes.

Because Edge service responses arrive already encoded as MP3, test the stages separately:

```text
raw Edge service chunk
current/historical batch assembly
current rich/direct assembly
candidate assembly
final output metadata/duration reporting
```

If the raw Edge chunk is already fuzzy, final re-encoding cannot restore lost detail. If the raw chunk is clean but the assembled result is fuzzier, investigate avoidable decode/re-encode cycles, export settings and final encoding.

Once Edge audio is received, avoid **avoidable** additional lossy generations. A single deliberate final encode may still be appropriate when assembly requires PCM-domain silence/trim/fade operations; this plan does not demand a technically awkward no-reencode solution if listening evidence says the simple path is better.

## 9. Semantic Boundaries and Segmentation Research

Text segmentation must preserve source content and understand **why** a boundary exists, but v0.6.5 should not replace a working tokenizer merely for novelty.

Useful semantic reasons include:

```text
CONTINUATION
SENTENCE
PARAGRAPH
CHAPTER
END_OF_BOOK
```

A model-limit continuation split is not automatically a sentence/paragraph pause.

The QA corpus should cover common false boundaries such as:

```text

e.g. / i.e. / vs.
initials
decimals
times such as 12:30
ratios such as 3:1
URLs
ellipses
quoted dialogue
closing quotes/brackets after punctuation
parentheticals
```

### Segmentation implementation research

During Phase 4, compare the existing NLTK/Punkt-based behavior with a mature alternative such as `pysbd` **only if the baseline demonstrates meaningful segmentation defects or the candidate can materially simplify a fragile rule set**.

Requirements for any selected approach:

- every intended source-content span survives segmentation exactly once and in order;
- no unintended omission, duplication or reordering;
- punctuation/whitespace/context needed for correct speech is preserved or deliberately normalized;
- backend maximum-input limits remain enforced;
- difficult dialogue/abbreviation examples are covered by regression tests.

Adding `pysbd` is not pre-authorized. Prefer the existing dependency set when quality/correctness are equivalent.

Do not create a growing list of book-specific regex hacks.

## 10. Audio Assembly Rules

### 10.1 Assembly is the first production-quality seam to investigate

After synthesis, prefer lossless/PCM-domain processing where it genuinely reduces repeated lossy generations and keeps the implementation simple.

Kokoro and Chatterbox already have strong PCM-oriented paths. Edge should gain only the minimum candidate seam needed to prove whether assembly is responsible for audible fuzziness or boundary defects.

### 10.2 Silence trimming

Trimming is optional and must remove only demonstrated excess service/model padding.

Candidate behavior should:

- inspect leading/trailing boundaries rather than blindly deleting internal silence;
- preserve a speech-side guard region;
- record enough before/after evidence to understand what was removed;
- compare current behavior, no-trim behavior, and conservative absolute/relative-energy candidates only where useful.

A relative-RMS detector is a valid research candidate, not a required final algorithm.

Internal long silence should first be **reported** for QA. Destructive internal silence shortening requires evidence that the silence is artificial and a clear semantic rule for why it is safe to change.

### 10.3 Intentional semantic pauses

Sentence/paragraph/chapter silence is not the same as an accidental chunk seam. Preserve semantic intent. Do not overlap voiced material across an intentional pause simply because another project uses crossfade stitching.

### 10.4 Continuation joins

A tiny crossfade or micro-fade may be tested for a technical continuation split inside otherwise continuous prose. Candidate values may include zero and very small overlaps, but no value is mandated by this plan.

Reject a crossfade that smears consonants, shortens natural prosody, or sounds worse.

### 10.5 Click handling

For a genuine discontinuity, prefer the least invasive successful correction: a suitable zero crossing, tiny fade toward/from silence, or similarly bounded treatment.

### 10.6 Sample rates

Use backend-native/actual sample rates. Resample only when required for a specific assembly operation, and avoid repeated conversions.

Do not force all engines to 24 kHz simply for symmetry.

## 16. Controlled A/B Method

Any meaningful quality change must be compared against an established baseline and should isolate one variable at a time.

### Edge assembly experiments

Where practical:

1. obtain one set of raw Edge service responses;
2. feed the same raw audio into baseline and candidate assembly paths;
3. compare audible output, duration/metadata correctness and processing cost.

This prevents network/model variation from masquerading as a stitching improvement.

Also compare generation/processing speed so a tiny theoretical quality improvement does not silently destroy the historically good batch throughput.

### Local engines

Use fixed-seed/deterministic QA only where the backend legitimately supports it. Do not add a production seed control merely for tests.

### Listening labels

Use neutral labels (`A`, `B`, `C`) rather than names such as `old-bad` / `new-improved` where practical.

### Decision ownership

The CLI agent prepares evidence and explains the isolated variable. It must not choose a subjective winner on the maintainer's behalf.

For research-heavy Phase 5 work, the expected workflow is iterative:

```text
CLI experiment -> stop/report -> maintainer + ChatGPT review/listen -> next bounded CLI prompt
```

The active plan defines the durable boundaries; exact candidate values and follow-up experiments may evolve from evidence.

## 22. Definition of “Excellent Voice Quality”

A final voice is accepted only when the applicable mechanical evidence and human listening agree.

### Layer 1 — Source/text correctness

Every intended source-content span survives segmentation exactly once and in order, with no unintended omission, duplication or reordering.

Any deterministic text/prompt normalization applied afterward must be documented enough to understand, preserve intended spoken content, and remain general rather than becoming a hidden book-specific pronunciation map.

### Layer 2 — Structural correctness

No backend input exceeds its proven safe limits; boundaries, retries and cancellation remain valid; assembly uses the intended semantic reason rather than one blunt pause rule.

### Layer 3 — File/acoustic correctness

No unexpected truncation, corrupted duration reporting, clipping, severe loudness outlier, unexplained/pathological long silence, digital click, duplicate pause, broken decode, or avoidable quality loss is accepted.

Not every harmless measurable difference needs correction.

### Layer 4 — Human acceptance

The actual audiobook voice sounds natural enough for sustained listening, with acceptable pronunciation, pacing and joins.

Layer 4 is mandatory. A better metric cannot overrule a failed listening test, and an architectural cleanup is not a quality improvement unless the listener agrees.
