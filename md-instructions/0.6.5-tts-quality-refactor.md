## 1. Core Principles

Cite these by ID everywhere else in this document and in primary coding-agent
prompts. Don't restate them — reference them.

- **P1 — Preserve-first.** Preserve behavior that already sounds good; change
  only the smallest seam that explains a *demonstrated* defect. A measurable
  timing/architecture improvement that sounds worse is a regression.
- **P2 — Investigation order.** When a defect is observed, investigate in this
  order unless evidence clearly points elsewhere: (1) source text/segmentation
  correctness, (2) where/why audio units are split, (3) assembly/rejoining and
  inserted silence, (4) avoidable re-encoding/bitrate/container metadata, (5)
  only then backend generation parameters.
- **P3 — No preselected recipe.** Don't assume a specific numeric value or
  technique (a dBFS trim threshold, a crossfade duration, a pause length,
  forced resampling, loudness normalization) is required before a demonstrated
  local defect justifies testing it as a candidate.
- **P4 — External references are references, not dependencies.** Inspect the
  actual source of any external project before borrowing a technique; never
  vendor/submodule it; never add a new dependency without a proven local
  benefit *and* maintainer approval; check license/attribution before reusing
  code; reject a technique that sounds worse even if a metric improved.
- **P5 — Local evidence outranks generic advice.** Evidence from the exact
  pinned engine versions and this repo's own tests/history outranks generic
  audiobook-tool advice, other repos, or LLM/search summaries.
- **P6 — Human ears are the final gate.** Mechanical/acoustic metrics
  (loudness, silence intervals, clipping) are supporting evidence only. A
  human listening pass is mandatory and authoritative for any audio-quality
  decision. No agent — local model, primary coding agent, or the ChatGPT
  planning layer — declares a subjective audio winner on the maintainer's behalf.
- **P7 — Manual gates are hard stops.** Green automation never implies manual
  approval. The agent does not advance to the next phase, merge to `master`,
  tag, publish a release, or delete a retained branch on its own judgment.
- **P8 — Source integrity.** Never modify imported source files or protected
  reference recordings (e.g. Chatterbox conditioning audio). Every
  transformation writes to a copy. A missing/hash-mismatched reference reports
  "setup required" — never substitute or auto-fetch a replacement.
- **P9 — No one-off pronunciation hacks.** A mispronunciation is evidence about
  sampling stability, text context, segmentation, or engine behavior — not
  permission to hard-code a word-specific replacement. If it can't be fixed
  generally, document and defer to the maintainer rather than patching the one
  word.
- **P10 — Provenance affects placement, not quality.** Whether a file was
  added directly or discovered via folder import may control output
  organization/mirroring, but must never silently select different
  audio-quality behavior.
- **P11 — Minimal diff, stay in bounds.** Implement only the current phase's
  objective. Don't opportunistically start later-phase work. Reuse shared
  foundations rather than building a parallel architecture.
- **P12 — Lightweight reproducibility.** Record enough to redo/understand an
  experiment (commit SHA, corpus identity, voice/backend, effective settings,
  output path) — but only fields that answer a real debugging question. Don't
  build a large experiment database.
- **P13 — No byte-hash quality contracts.** Never use audio-byte hashes as a
  correctness check for nondeterministic/network TTS output. Correctness comes
  from source-span/segmentation invariants, duration/decode checks, and human
  listening — not byte-for-byte reproducibility.

- **P14 — Workers are file-level and adaptively capped.** `Workers = X` is a
  requested **whole-file concurrency** level, never permission to parallelize
  chunks from one source file. One worker owns one source file and processes
  that file's internal text/chunks sequentially and in order; other workers
  handle other files. Effective concurrency is bounded by:

  ```text
  min(user-requested workers,
      queued source files,
      backend-safe limit,
      conservative device-safe limit)
  ```

  The device-safe limit may consider CPU capacity, available system RAM,
  GPU availability, VRAM, measured backend/model footprint, and necessary
  headroom for the OS/UI/FFmpeg/buffers. Do not guess one universal fixed cap.
  An extreme request such as `100` must safely reduce to what the current
  machine/backend can support and truthfully report requested vs. effective
  workers. Edge and Kokoro should honor the requested count up to safe limits.
  Chatterbox keeps its current effective one-file-at-a-time safety limit until
  mutable model/conditioning state is proven safely isolated for multiple
  simultaneous files; never obtain concurrency by racing shared state.

## 7. Segmentation, Assembly & Measurement Research (P1–P4)

**Segmentation.** Preserve semantic boundary reasons (`CONTINUATION`,
`SENTENCE`, `PARAGRAPH`, `CHAPTER`, `END_OF_BOOK`) — a model-limit split is not
automatically a sentence/paragraph pause. QA corpus must cover common false
boundaries: `Mr./Mrs./Dr./Prof.`, `e.g./i.e./vs.`, initials, decimals, times
(`12:30`), ratios (`3:1`), URLs, ellipses, quoted dialogue, closing
quotes/brackets after punctuation, parentheticals. Compare NLTK/Punkt against
`pysbd` **only** if the baseline shows a real segmentation defect or `pysbd`
would materially simplify a fragile rule set (P3, P4) — adding it is not
pre-authorized.

**Assembly.**
- Prefer lossless/PCM-domain processing where it reduces repeated lossy
  generations without adding complexity.
- Silence trimming is optional, inspects leading/trailing boundaries (not
  blind internal deletion), preserves a speech-side guard, and records
  before/after evidence. Internal long silence is *reported* first;
  destructive shortening needs evidence it's artificial.
- Sentence/paragraph/chapter silence is intentional — don't crossfade over it.
  A tiny fade/crossfade may be tested only for a technical continuation split,
  and only if it doesn't smear consonants or shorten prosody.
- Use backend-native sample rates; resample only when an operation requires
  it — do not force 24 kHz everywhere for symmetry.

**Loudness/measurement (lightweight by default).** The harness may record
integrated loudness, peak/true-peak, RMS/peak stats, clipping, suspicious
silence — as diagnostic evidence, not a mandate to refactor. No default
normalization; investigate only if listening demonstrates a real whole-file
inconsistency. If later authorized, use a true two-pass FFmpeg `loudnorm`,
not simple peak normalization mislabeled as "EBU R128."

**STT verification — deferred.** No Whisper/faster-whisper in v0.6.5. Rely on
source-span invariants, chunk-size limits, decode validation, duration
sanity, suspicious-silence detection, and mandatory listening. At Phase 9,
record whether any missing/repeated/truncated-speech defect escaped these
non-STT gates — only then consider STT as a future separate plan.


**Worker/concurrency model (P14).**
- Concurrency is **between source files only**. A worker that claims a file
  remains responsible for that file while its internal synthesis units are
  processed sequentially in source order; do not schedule chunks from the same
  source file onto multiple synthesis workers.
- Resolve an **effective worker count at run start** from the requested count,
  queued-file count, backend safety, and a conservative device/resource cap.
  Preserve headroom rather than trying to consume every CPU/GPU/RAM/VRAM unit.
- The exact resource heuristic is implementation/research-owned. Measure real
  backend footprint where useful; do not encode a fake hardware formula merely
  to look adaptive.
- Edge and Kokoro should use multiple file workers when their backend/resource
  evidence says it is safe. Chatterbox above one concurrent file requires
  proof that mutable model/conditioning state is isolated correctly; otherwise
  its truthful backend-safe cap remains `1`.
- **Concrete Chatterbox >1 proof:** run at least two different source files
  concurrently using two clearly different reference-conditioning inputs.
  Mechanically instrument/verify that each file keeps its assigned reference/
  conditioning/model state and that no shared mutable state can cross-contaminate
  the other file. Then preserve both concurrent outputs for a maintainer listening
  gate confirming that each remained the intended voice. Do **not** add a speaker-
  embedding, voice-recognition, or other new runtime dependency solely to automate
  this proof. If safe isolation cannot be demonstrated with a bounded change and
  direct evidence, keep the truthful Chatterbox cap at `1`.
- The run log/status must make capping visible, e.g. `Requested workers: 100 |
  Effective workers: 4`, rather than silently ignoring the setting.
- Pause/Resume/Cancel/Retry Failed and output planning must remain correct under
  >1 effective file worker. An oversized request must degrade safely, not OOM,
  thrash the machine, corrupt output, or change text/chunk ordering.

## 8. QA Corpus, Harness, Baseline & A/B Method (P4, P6, P12, P13)

generated audio stays ignored): neutral narration, dialogue, the difficult-
tokenization list above, structural/join stress text crossing backend chunk
limits, and a ~5,000-character sustained-narration passage (adjustable) plus
a longer stress passage for representative voices. Promote only the smallest
fixture+test needed to guard a *durable, discovered* defect into `files/tests/`.

**Harness.** Extend `generate_voice_samples.py` rather than building a
parallel QA tool; preserve all historical modes including the four-voice
Chatterbox evaluation; a new `--quality-suite` mode may be added. Manifest
fields per P12: commit SHA, corpus identity, voice/backend, synthesis/assembly
path identity, effective settings, sample rate/bitrate, duration, throughput,
basic loudness/silence evidence, output path.

**Tracked Edge-test network rule.** Ordinary tracked unit/regression tests must
not require a live Microsoft Edge TTS network call. Follow the repository's
existing convention by mocking/stubbing the Edge service boundary while testing
segmentation, assembly, job control, importing, and other deterministic behavior.
Real Edge synthesis is reserved for explicitly authorized integration/manual QA
steps such as baseline capture and listening gates. A transient network outage
must not make the normal tracked pytest suite fail.

**Baseline (before any production change):** short difficult-text sample for
every retained voice; sustained/longer baselines at minimum for Edge
Steffan/Jenny, Kokoro Heart/Michael, Chatterbox Female 1/Male 1; the
historical v0.5.0 Edge batch reference reproduced where practical; raw
Edge-chunk vs. final-output comparison; matched direct-file vs.
folder-import comparison. Don't call an older/differently-structured path
inferior without listening evidence (P1).

**A/B method.** Isolate one variable at a time — same raw Edge audio through
baseline vs. candidate assembly; compare audible output, metadata correctness,
*and* processing cost/throughput so a small quality tweak doesn't quietly
kill the historically good batch speed. Use neutral labels (`A`/`B`/`C`), not
"old-bad"/"new-improved." The agent prepares evidence and stops (P6) —
research-heavy Phase 5 work is iterative: `experiment → stop/report →
maintainer + ChatGPT review/listen → next bounded prompt`.

## 12. Agent Roles & Delegation Boundaries

Three tiers, three different authorities:

**Primary coding agent — Claude Code or Codex CLI.** The maintainer may choose
either for a bounded phase/task. Use one primary implementation owner at a time
for that bounded unit so two agents are not editing the same production surface
concurrently. The primary coding agent may edit `scripts/Universal/tts/`,
tracked tests, and project docs within the active phase; it follows §13/P7 and
reviews/accepts or rejects every local-model draft before any of it becomes
tracked/production work.

**ChatGPT planning layer — owner of the plan/decision prompts.** Reviews
repository evidence and listening results with the maintainer, refines
research decisions, and drafts the next bounded Claude Code/Codex prompt or a
gate-failure fix prompt (§14). It does not directly edit the repository unless
the maintainer explicitly asks. A routine prompt can remain short:

> Reorient from the repository, `AI-WORKSPACE.md`,
> `md-instructions/Handoff.md`, and the active v0.6.5 plan. Implement Phase N
> exactly within its bounds, citing P-codes as needed. Stop at its gate and
> report. Do not start Phase N+1.

**Optional local Ollama worker(s)** (`qwen`/`deepseek`/`llama`; verify the exact
pulled tag before use) are mechanical accelerators only. If
`files/dev-work/qwen_worker.py` is present, the primary agent may use it for
low-judgment work; the helper is ignored/local developer tooling and is **not a
release dependency**.

**Before first delegation in this plan, and only if the helper is actually going
to be used,** the primary agent validates its containment contract: an allowed
write inside the resolved repository `files/dev-work/` root succeeds; an outside
path and a symlink/`..` escape are refused; a refused destination receives no
requested output and no failure sidecar; prompt-file/stdin input works; and a
simulated/model failure cannot leave an apparently successful result. This is a
local-tool safety check, not a v0.6.5 release prerequisite. If the helper is
absent or fails validation, do the task directly with the primary agent.

Allowed local-worker tasks:
- summarize/parse large log, pytest, ffmpeg, or measurement output;
- compute/report mechanical acoustic statistics from already-generated files;
- format/diff text or structured evidence;
- draft repetitive boilerplate around test assertions/requirements that the
  primary agent has already specified.

Local-worker hard boundaries:
- no subjective listening/pass-fail decisions;
- no interpretation or amendment of this plan;
- no independent architecture, pronunciation, dependency, or invariant choice;
- no direct writes to production code, permanent docs, or tracked tests;
- generated/draft file outputs use a **realpath allow-list**, not a deny-list:
  the resolved destination and its success/failure sidecar must both remain
  inside the repository's resolved `files/dev-work/` root. Absolute paths, `..`,
  or symlink traversal must not escape that root;
- a protected/refused path must not receive either the requested output **or**
  a failure sidecar;
- failures exit non-zero, never leave a result file that can be mistaken for
  success, and may record `"ok": false` metadata only inside the allowed
  `files/dev-work/` area;
- successful delegated output is trusted only when its sidecar says
  `"ok": true` **and** the primary coding agent has reviewed the content;
- support a prompt-file/stdin path for long inputs so Windows command-line
  length is not the practical context limit;
- write success output/metadata so a partial metadata-write failure cannot
  leave an apparently accepted result without its required success record.

If the local helper is absent, unsuitable, or fails, the primary coding agent
continues directly; no phase depends on local-model availability.

## 14. Manual Gate Failure / Rollback Protocol

When a manual gate (listening, UI/layout, platform validation) is **rejected**:

1. **Stop.** The primary coding agent does not auto-fix or advance. The phase
   stays open.
2. **Capture the failure.** Maintainer records the exact gate, the specific
   artifact (voice/file/sample/timestamp), and a plain description of the
   defect.
3. **Escalate to the ChatGPT planning layer.** Maintainer shares the raw
   failing artifact plus the description. ChatGPT inspects it, forms a
   hypothesis grounded in §1's Core Principles and the phase's bounds, and
   decides the smallest corrective instruction.
4. **ChatGPT drafts a bounded primary-agent prompt** that: targets only the
   failed gate's phase and files; cites the specific P-codes that apply;
   states the exact defect and evidence, not "make it better"; follows the
   format in `AI-WORKSPACE.md`; explicitly forbids unrelated changes.
5. **The primary coding agent implements the fix**, re-runs the phase's mechanical gates,
   and stops again at the *same* manual gate — it does not decide on its own
   that the fix is good enough to move on (P7).
6. **Re-review.** Pass → resume the phase sequence. If substantially the
   same symptom fails the same gate **twice in a row**, stop the local patch
   loop and return to maintainer + ChatGPT for root-cause reassessment. For an
   audio-quality defect this may reopen Phase 3/4/5; for a UI/platform/
   concurrency defect, reopen the relevant seam instead. Do **not**
   automatically jump phases or apply a third symptom patch without a new
   bounded hypothesis.
7. **Record it.** Short entry in `Handoff.md`/`Decisions.md`: what failed,
   what was tried, what fixed it (or that it's still open) — so a later phase
   or a fresh agent context doesn't repeat the same failed experiment.

## 17. Definition of "Excellent Voice Quality"

A voice is accepted only when mechanical evidence *and* human listening
agree:

1. **Source/text correctness** — every source span survives segmentation
   exactly once, in order; any text normalization is documented, preserves
   intent, and stays general (P9).
2. **Structural correctness** — no backend input exceeds proven safe limits;
   boundaries/retries/cancellation stay valid; assembly follows the intended
   semantic reason, not one blunt pause rule.
3. **File/acoustic correctness** — no unexpected truncation, corrupted
   duration, clipping, severe loudness outlier, pathological silence, click,
   duplicate pause, or broken decode. Not every harmless measurable
   difference needs correcting.
4. **Human acceptance (mandatory, P6)** — sounds natural enough for sustained
   listening, with acceptable pronunciation, pacing, and joins. A better
   metric cannot overrule a failed listening test.
