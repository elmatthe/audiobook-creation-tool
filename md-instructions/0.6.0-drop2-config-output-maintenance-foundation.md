## 3. Goal

Create one safe, tested shared foundation that:

1. loads a documented committed root `config.toml` without making startup fragile;
2. resolves effective values using code defaults → validated TOML → allowlisted mutable user settings;
3. gives all tools a consistent, configurable, collision-safe output model;
4. implements the confirmed flat-file, mirrored-folder, Cover Image, and M4B Maker destination rules;
5. gives users a clear Preferences and Data surface with separate Reset Preferences and Clear Downloaded Data actions;
6. deletes only explicitly selected regenerable assets, using a safe post-exit path when `.venv` or open files are involved;
7. includes `config.toml` in both release archives; and
8. permanently protects the exact documentation filenames requested by the maintainer.

## 6. Detailed design contract

### 6.1 Root `config.toml`

Use Python's standard-library `tomllib`; Python 3.11 is already the project minimum. Keep comments that explain supported keys and examples. The committed file must contain at least:

| TOML key | Type and committed default | Runtime behavior |
|---|---|---|
| `project.name` | string, `Audiobook Creation Tool` | Project metadata; validated nonblank |
| `project.version` | string, current `0.5.1` | Must match `shared/version.py`; runtime fallback is code version; verification fails drift |
| `project.python_min` | string, `3.11` | Metadata/preflight contract; verification checks supported format |
| `project.entry_point` | relative string, `scripts/Universal/launcher.py` | Must resolve to the expected in-repository file |
| `project.platforms` | array of strings, Windows and macOS | Metadata; only known values accepted |
| `output.base_directory` | string, empty | Empty means platform default `~/Downloads/Audiobook-Creation-Tool-Outputs`; nonempty accepts an absolute path or `~` path |
| `logging.max_sessions` | integer, `30` | Valid range 1–1000; invalid values fall back to 30 |
| `importing.large_result_warning_threshold` | integer, `1000` | Validated now; consumed by Plan 3, not used to implement Plan 3 behavior in this drop |

Do not expose unsafe structural paths, cleanup targets, arbitrary command strings, or executable paths as user-overridable TOML keys in this drop. Do not expand environment variables in path values. Do not treat a relative output base as the current working directory; reject it with a warning and use the default.

The committed file is machine-agnostic. A user-selected absolute output path belongs in `settings.json`, not in a Git commit.

### 6.2 Effective configuration and precedence

Implement one typed, immutable effective snapshot with source diagnostics:

1. immutable code defaults;
2. valid supported values from root `config.toml`;
3. valid values from an explicit mutable-setting overlay allowlist.

For this drop, the only mutable setting that overlays a TOML configuration key is the GUI-selected output base. Existing user-state keys—such as `last_tool` and remembered input/cover dialog directories—remain valid settings but are not invented as TOML keys.

Requirements:

- Validate per key. One bad value must not discard unrelated good values.
- Missing or malformed `config.toml` must not prevent startup; use defaults and emit diagnostics.
- Unknown keys/sections are ignored and reported once so typos do not silently appear supported.
- Malformed or invalid `settings.json` uses defaults and reports a useful diagnostic without rewriting the file during load.
- Warnings identify source and key, explain the fallback, and avoid raw stack traces in the Summary message.
- Log technical details. Present one nonblocking configuration-warning summary per application launch after the root window is ready; do not show one modal per key or per tool.
- Provide deterministic reload/cache invalidation for tests, Reset Preferences, and a changed output preference.
- A running operation captures its destination/effective values at run start. A later preference change affects only later runs.
- The GUI writes only allowlisted mutable settings through atomic JSON replacement and never rewrites the committed TOML.

### 6.3 Preferences and Reset Preferences

Add one clearly named launcher entry point such as `Preferences & Data…`, available on both platforms. The dialog contains:

- the effective output base;
- a `Use default Downloads location` choice;
- a browse action for a user-selected absolute output base;
- a short indication of whether the effective value came from code/default TOML or the user preference;
- `Reset Preferences` as a separate action; and
- a clearly separate entry to `Clear Downloaded Data`.

Reset Preferences:

- requires a normal confirmation, not the stronger cleanup confirmation;
- clears mutable app/user settings, including last tool, remembered dialog directories, and output-base override;
- does not edit `config.toml`;
- does not delete `.venv`, models, portable binaries, logs, outputs, or source media;
- leaves the application in a valid default state and refreshes effective configuration immediately;
- uses an atomic settings operation and reports failure rather than silently claiming success.

### 6.4 Output base, tool folders, and run reservation

The default layout is:

`<Downloads>/Audiobook-Creation-Tool-Outputs/<Tool>-Outputs/<Tool>-N/`

Retain the current stable slugs from `shared.paths.TOOL_SLUGS`:

- `TTS-Audiobook`
- `M4B-Converter`
- `MP3-Tool`
- `M4B-Maker`
- `Cover-Image`
- `M4B-Metadata`

Requirements:

- Centralize the registry; do not duplicate slugs in tool panels.
- Validate a configured/preferred base before a run. If it cannot be created or written, show a useful error and do not start processing.
- Reserve the lowest available positive run number atomically with `mkdir`, retrying collisions. Do not use a check-then-create race.
- Reserve a run directory at validated run start, not at `build_ui()` time. Merely opening or switching to a tool creates no output folder and does not freeze a number for the whole app session.
- One run uses one reserved directory. A later run reserves a new one.
- If validation/cancellation ends before any output and the reserved run directory is still empty, it may be removed best-effort; never remove a nonempty directory.
- Keep a compatibility wrapper only where necessary during migration; no tool may continue computing its own competing run directory after Phase 4.

### 6.5 Collision and path-safety service

Provide shared, pure path-planning functions and an atomic reservation/write boundary where needed.

- Try the requested safe filename first; on conflict use `stem-1.ext`, `stem-2.ext`, and so on.
- Treat planned duplicates within the same batch as collisions even before files exist.
- Preserve the complete suffix and produce valid names on Windows and macOS.
- Reject or safely normalize path separators, `.`/`..`, empty names, control characters, and Windows reserved device names.
- Compare resolved paths to prevent input==output and output escape.
- Never follow a symlink/junction to establish an output destination.
- Default operations remain contained within the reserved run directory. Only the explicit Cover source-side and M4B Maker custom-destination modes may change that root.
- Make collision results deterministic for a deterministic input order.
- Preserve current read-only-input guarantees in every tool worker.

### 6.6 Flat individual-file and mirrored folder-root rules

The shared service accepts already-discovered source items; it does not implement Plan 3 scanning.

- Individually selected files from any number of source locations output directly into the one run directory. Do not recreate their parent trees.
- Filename conflicts use collision-safe numbering such as `Book-1.m4b`, `Book-2.m4b`.
- For one folder-import root, mirror each source's safe relative parent path directly under the run directory.
- For multiple folder-import roots, create collision-safe named root containers under the run directory, then mirror each root's relative hierarchy inside its container.
- Reject absolute relative paths, `..` traversal, and paths that resolve outside the selected output root.
- Preserve the existing TTS folder-batch behavior while routing it through the service. Plan 3 later owns generalized discovery/traversal.

### 6.7 Tool integration

Migrate existing output producers narrowly. Do not redesign unrelated inputs, metadata, workers, or progress controls.

- TTS Audiobook: preserve single-file and current PDF/TXT folder-batch behavior, including its existing mirroring and Edge timing limitations; use the shared output snapshot.
- M4B Converter: current operations use the standard flat/run service; do not add split/metadata modes from Plan 5.
- MP3 Tool: current operations use the standard service; do not simplify its workflow or add multi-book behavior from Plan 8.
- M4B Metadata Editor: preserve copy-only output and input protection while using the standard service; do not add per-M4B pages or Shared Metadata behavior.
- M4B Maker and Cover Image: default modes use the standard service; their confirmed exceptions follow Section 6.8.

`<base>/Cover-Image-Outputs/Cover-Image-N/`

### 6.9 Downloaded-data catalog

Clear Downloaded Data displays an itemized inventory with present/missing state, estimated size, consequences, and a checkbox for each supported asset:

| Asset ID | Project-owned target | Consequence |
|---|---|---|
| `virtual_environment` | root `.venv/` | Dependencies rebuild on next launch; always post-exit |
| `portable_binaries` | `files/bin/` contents | Project may re-download portable ffmpeg; never remove system ffmpeg |
| `downloaded_models` | `files/runtime-data/models/` contents | Kokoro/Hugging Face data downloads again when needed |
| `application_logs` | `files/runtime-data/logs/` contents | Diagnostic history is removed; open log requires post-exit handling |

Do not add developer caches, user outputs, source/test fixtures, settings, configuration, or arbitrary directories to this catalog. If the audit finds another genuinely downloaded, regenerable, project-owned runtime directory, stop and request approval before adding a new asset ID.

The selection screen defaults to no destructive selection unless the user has explicitly chosen otherwise. Confirmation must list the selected items, size estimate, restart/rebuild effects, and that the app will close. Reset Preferences remains a separate action and is never silently bundled.

### 6.10 Cleanup request, worker, and result

The GUI process must never recursively delete the interpreter it is running from.

Implement a versioned cleanup request containing only:

- schema version;
- selected enumerated asset IDs;
- requesting process ID and creation time;
- a request identifier; and
- non-path presentation metadata if needed.

The worker maps asset IDs to compiled project path constants. The request must not carry arbitrary delete paths. Before every deletion:

- resolve the expected repository root from the worker's own file location;
- verify the target equals the exact allowlisted path for its ID;
- verify containment for non-root assets;
- refuse symlinks/junctions/reparse-point surprises rather than following them;
- refuse the repository root, `scripts/`, `md-instructions/`, `files/tests/`, settings, config, launchers, source media, and output bases;
- handle missing targets as a successful no-op;
- delete contents/targets with explicit error collection rather than hiding failures.

Coordinate through the existing stdlib bootstrap/root-launcher boundary so the cleanup process does not run from the venv being removed. Preserve quoting for repository paths containing spaces and apostrophes. Preserve no-visible-console normal launch behavior. The sequence is:

1. validate selection and write the request atomically under a small maintenance-state directory outside every selectable target;
2. start a detached non-venv cleanup coordinator and prove it accepted the request;
3. close the GUI;
4. wait for the requesting GUI process to exit;
5. perform only the allowlisted deletions;
6. atomically write a success/partial-failure result outside the deleted asset paths;
7. remove or mark the consumed request; and
8. show the prior cleanup result on the next launch, with a useful recovery path if anything failed.

Do not auto-loop, retry forever, or claim success before deletion completes. If the coordinator cannot start, keep the app open, report the failure, and do not schedule cleanup.
