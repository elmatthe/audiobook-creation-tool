# Frozen UI Contract

## 1. Global principles

All six tools share:

- compact Tkinter/ttk-sized controls;
- the existing dark/navy **outer application shell** substantially unchanged;
- one global remembered **Light / Dark** appearance setting;
- one consistent Activity/log presentation;
- standardized importer/list interaction where applicable;
- compact numbered workflow sections;
- keyboard-accessible core controls;
- **no scrolling of the core panel itself**.

Light is the first-run default. Store one user/runtime preference (for example `appearance = "light" | "dark"`), not one setting per tool and not in committed `config.toml`.

Place one global shell toggle near `Preferences & Data...`, with text + icon:

- Light active: `☾ Dark mode`
- Dark active: `☀ Light mode`

Theme switching is presentation-only and must preserve all imports, entered values, selected Book/page, logs, progress, frozen snapshots, retries, and running jobs.

App-owned secondary dialogs should follow Light/Dark. Native OS file/folder dialogs remain native.

### No-core-scroll release contract

At minimum supported size:

- Windows: **920×600**
- macOS: **1024×800**

all core controls needed to use the tool must remain reachable without scrolling the whole panel.

Scrolling is allowed **inside** naturally scrollable content only: import/track lists, chapter editors, thumbnail/file browsers, logs/activity text, etc.

When space is tight:

1. reduce padding/chrome;
2. reflow compact controls;
3. reduce flexible list/log height;
4. preserve every required control.

Do not solve layout defects with a whole-panel Canvas/scrollbar or by silently increasing minimum size.

When the window grows, flexible lists/editors/browser/activity areas grow; buttons/fields/settings remain compact.

## 2. Two approved layout families

### Family A — guided left/right workflow

Tools:

- **TTS Audiobook**
- **M4B Converter**
- **Cover Image**

Layout:

- left: numbered workflow, roughly **32–35%**
- right: Activity, roughly **65–68%**
- fixed responsive split; no draggable sash

Use compact bordered/LabelFrame-style sections, not large cards.

#### TTS Audiobook

**Layout is frozen as the reference.** Keep its present structure:

1. Sources
2. Voice & Audio
3. Output & Run
4. Activity on the right

No layout redesign or cosmetic spacing project. Only changes required for shared appearance/import/activity contracts are in scope.

#### M4B Converter

Reorganize to:

1. **Sources**
2. **Conversion & Metadata**
3. **Output & Run**
4. Activity on the right

Inside Section 2, make **Output structure** visually obvious at the top:

`Whole book` / `Split by chapter`

Then quality and metadata controls.

Replacement metadata fields remain visible but disabled when not applicable; avoid layout jumping.

Preserve all converter functionality and policy.

#### Cover Image

Reorganize to:

1. **Sources**
2. **Resize Options**
3. **Output & Run**
4. Activity on the right

Keep Details / List / Medium Thumbnails as source-browser views. The source browser is the main flexible region on the left.

Do not invent new resize behavior for symmetry.

### Family B — dense multi-Book workflow

Tools:

- **MP3 Tool**
- **M4B Maker**
- **M4B Metadata**

Preserve their current major geometry, Book/page model, Shared/Current Book organization, and overall control positioning. Do **not** force Activity to the side.

Retire the oversized ACT-styled interior appearance; use the same compact visual language as Family A.

Conceptual hierarchy:

1. **Import & Books**
2. **Book Settings / Metadata**
3. **Tool-specific contents & run**
4. Activity below

Tool wording:

- MP3 Tool: `1. Import & Books` → `2. Book Settings` → `3. Tracks & Run`
- M4B Maker: `1. Import & Books` → `2. Book Settings` → `3. Tracks, Chapters & Build`
- M4B Metadata: `1. Import & Books` → `2. Metadata` → `3. Chapters & Save`

### Shared vs Current Book

In all three dense tools:

- Shared uses a restrained cool blue/blue-grey tinted surface, stronger border/header, and explicit text such as `Shared — applies to every Book and overrides its own value`.
- Current Book uses the normal panel surface and quieter border.
- Same semantic distinction in Light and Dark.
- Avoid saturated warning colors for normal Shared state.

## 3. Universal Activity component

All six tools use the **same visual Activity design**:

- `Summary | Detailed`
- `Clear Log`
- progress/status arrangement
- font/spacing/borders
- Light/Dark treatment
- empty/running/disabled presentation
- internal scrolling behavior

Only the **log content/messages** differ by tool.

Placement:

- TTS / Converter / Cover: right side
- MP3 / Maker / Metadata: bottom

On dense tools, Activity may shrink vertically before required settings/actions disappear; the Activity contents can scroll.

## 4. Universal importer/list interaction

Where applicable, use one compact convention:

`[list/browser]`

`Add Files | Add Folder | Move Up | Move Down | Remove | Clear All`

then file-type/import options.

Only omit controls that genuinely do not apply.

When an ordered list has focus:

- Ctrl/Cmd+A = Select All
- Shift-click = range selection
- Ctrl/Cmd-click = additive/toggle selection
- Delete/Backspace = Remove selected where valid
- Alt/Option+Up/Down = move selected items
- multi-selection moves as a block while preserving internal order

Do not hijack normal text-editing shortcuts when focus is in Entry/Text/chapter-edit controls.

Prefer extending/reusing shared importer/list infrastructure over six local implementations.

## 5. Styling / accessibility

Light mode should remain close to the current compact classic Tkinter presentation.

Dark mode uses the same geometry/hierarchy with a neutral charcoal/dark-grey palette and restrained navy/blue accents. It should feel like the same UI with a dark appearance, not a second design system.

Compact controls are the default. One primary action per tool may receive restrained blue emphasis; destructive actions may use restrained warning/red treatment.

Disabled controls normally stay visible and greyed rather than appearing/disappearing.

Sections are always visible; no collapsible workflow sections.

Tab order should follow visible workflow where practical:

`Section 1 → Section 2 → Section 3 → Activity`

Do not force Windows-looking chrome onto macOS; preserve platform-appropriate compact behavior.
