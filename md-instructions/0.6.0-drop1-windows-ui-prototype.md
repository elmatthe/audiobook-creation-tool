## 2. Context

The application is a single shared tkinter/ttk codebase with six tools in one launcher. The current v0.5.1 architecture already provides important behavior that this prototype must preserve:

- `shared/ui_theme.py` selects macOS aqua/Finder styling or the classic Windows/other path and exposes fonts, geometry, minimum size, colors, metrics, mouse-wheel wiring, and `ProgressIndicator`.
- `launcher.py` owns the six-tool registry, availability checks, lazy build-once containers, tool switching, saved last-tool state, status text, and log-folder access.
- `m4b_metadata_editor.py` already has multi-file and folder import, shared-value detection, metadata fields, cover selection, auto-numbering, per-file chapter-title pages, copy-only output, clear-tags and remove-numbering actions, background workers, queue-based log/progress updates, and cooperative Cancel between files.
- The launcher starts at `1024x720` with a `920x600` minimum. Long forms and lists may scroll; primary actions and run status must fit when maximized at the reference size.
- macOS already has an approved Finder-style appearance. This drop must not redesign it.
- Current before-state screenshots are committed under `files/UI-Current-Screenshots/`.

Decision 39A requires the Windows launcher plus M4B Metadata Editor to prove the design direction before broader conversion. This is a meaningful layout, hierarchy, spacing, and interaction redesign—not a dark recolor of the current classic widgets.

## 3. Goal

Create a coherent, reusable Windows dark design system in the existing tkinter/ttk architecture and prove it in:

1. the Windows launcher shell; and
2. the Windows M4B Metadata Editor panel.

The result must preserve current behavior, provide deterministic automated and manual evidence, remain isolated from the other five tool panels, keep macOS Finder/aqua behavior intact, and receive explicit user screenshot approval before this drop can close.

- Any TTS, M4B conversion, MP3 processing, M4B making, Cover workflow, metadata-writing, output, or audio-engine change.
- A switch away from tkinter/ttk. If the prototype proves brittle or still looks materially dated, stop with evidence and request reassessment; do not change toolkit.

- Version bump, release tag, release ZIP, or published release.

## 7. Design and implementation requirements

### 7.1 Platform routing

- Keep one codebase and make the Windows path explicit; do not infer Windows by applying a global dark theme to every non-macOS platform.
- Preserve the macOS `aqua`/Finder path and its current colors, metrics, shell behavior, native controls, and tool availability.
- Preserve the historical Linux/other fallback unless a tiny compatibility change is unavoidable.
- Keep the returned theme bundle backwards-compatible in shape: mode, font family, heading/button fonts, geometry, minimum size, colors, and metrics remain available. Windows must now return centralized colors and metrics rather than scattering constants through panels.
- Keep the current launch geometry and minimum size unless the prototype demonstrates a specific problem. Any change needs evidence, tests, and an explicit explanation in the phase report.

### 7.2 Semantic tokens and styles

Centralize at least these semantic roles; exact values are approved through the screenshots rather than hard-coded by this plan:

- application background, primary surface, elevated surface, muted surface, border/divider;
- primary text, secondary text, disabled text;
- accent, accent hover/pressed, focus indicator;
- success, warning, and danger/status roles;
- input/list/text backgrounds and selection colors;
- Shared Metadata background, border, and header/accent;
- spacing, corner/border treatment, row heights, control padding, sidebar width, and content maximums where needed;
- body, small, heading, and action typography.

Requirements:

- Namespace ttk style names. Do not globally redefine base styles used by the five unconverted panels.
- Provide a small, clear shared API for applying tokens to classic Tk widgets (`Canvas`, `Listbox`, `Text`, and similar) that ttk cannot style directly. Avoid panel-specific color literals.
- Define and test normal, hover, pressed, selected, disabled, focus, and danger states where the widget supports them.
- Keep keyboard focus visible against every background.
- Preserve `ProgressIndicator`’s public API (`update`, `set_indeterminate`, `reset`, and `finish`) and its main-thread use contract.
- Do not add image assets merely to imitate controls that ttk can express robustly.

### 7.3 Layout and hierarchy

- Use cards/sections and spacing to create clear hierarchy; do not make the current layout dark without restructuring it.
- Keep primary actions and current run status visible at a maximized 1920×1080 window at both required scaling levels.
- Use deliberate scroll regions for file lists, long metadata forms, chapter editors, and logs. Do not promise zero scrolling.
- Avoid nested wheel traps. Preserve `enable_mousewheel` behavior, child-transition guarding, and expected Windows wheel direction.
- Do not clip text, focus rings, buttons, progress labels, or scrollbars at 125% scaling.
- Keep resize behavior stable down to the tested minimum size; if a region cannot fit, it should scroll or reflow rather than overlap.

### 7.4 Launcher behavior that must remain true

- All six tools appear in the existing order when available.
- A panel is built only on first selection, then hidden/shown rather than rebuilt.
- Panel state survives switching away and back.
- The saved last tool is restored when valid; fallback selection remains safe.
- Missing optional-tool errors and UI build failures stay understandable and localized.
- Status text and log-folder access continue to work.
- The launcher shell can be modernized; the five unconverted child panels cannot.

### 7.5 M4B Metadata Editor behavior that must remain true

Preserve all currently available controls and behavior, including:

- Add M4B, Add Folder, multi-selection, Remove Selected, and Clear List;
- readable single-file prefill and batch shared/varies detection;
- title, artist/author, album, year, genre, comment, series name, and Series Part handling;
- preserve-by-default series behavior and auto-number toggle/start value;
- cover browse/clear;
- per-file Previous/Next chapter pages, editable chapter-title text, and auto-number handling;
- output folder selection and collision-safe copy-only writes;
- Save, Clear All Tags while keeping chapters, and Remove Series Numbering while keeping unrelated tags/chapters;
- inputs disabled while busy, determinate progress, queue-driven log updates, Cancel between files, and proper return to idle;
- imported originals never being modified.

The visual refactor must not change metadata collection, field precedence, file order, output paths, filenames, tag namespaces, chapter logic, thread boundaries, or cancellation timing.
